== Context

The post-codegen verifier (`crates/typed-wasm-verify/`) enforces **L7
(aliasing)**, **L10 (linearity)**, and **L13 (module isolation, negative
form)** on emitted wasm today.  The only carrier it consults is the
`typedwasm.ownership` custom section (4-kind: `Unrestricted` /
`Linear` / `SharedBorrow` / `ExclBorrow` per function signature; renamed
from `affinescript.ownership` in PR #65 to make it producer-neutral).

`typedwasm.ownership` does not contain region/field schema, pointer
nullability, bounds cardinality, or capability data.  Without that
data, **L2 (region-binding), L3 (type-compatible access), L4 (null
safety), L5 (bounds-proof), L6 (result-type)**, and **L15 (resource
capabilities)** cannot be re-checked on emitted bytes — the source-level
checker (`MultiModule.idr`, `ResourceCapabilities.idr`, plus the
AffineScript `Checker`) is the only line of defence.

The Idris2 spec side already models all the required structure:

* `Region.idr` — `WasmType`, `Field`, `Schema`, `FieldIn`
* `MultiModule.idr` — `SchemaSub`, `ModuleCompat`, `noSpoofing`
* `Pointer.idr` — `PtrKind` (Owning / Borrowing / Exclusive),
  `Nullability` (NonNull / Nullable)
* `ResourceCapabilities.idr` — `CapabilitySet`, `DistinctCaps`,
  `ContainedIn`

So the gap is purely on the **wire** side: there is nowhere to put any
of this information when AffineScript or Ephapax emits wasm.  This is
an **ABI** problem, not an enforcement problem.

L14 (session protocols) and L16 (agent choreography) are out of scope
of this proposal: their language-surface work
(`session`/`choreography` declarations) is not yet emittable by any
producer; carrying their state on the wire is premature.

== Proposal

Add **two new producer-neutral custom sections** to the typed-wasm
ABI, distinct from `typedwasm.ownership`, both versioned and
lenient-readable in the same shape as the existing codec.

. `typedwasm.regions` — carries everything L2–L6 need.
. `typedwasm.capabilities` — carries the L15 capability lattice.

The two are split (rather than fused into one omnibus section) so a
producer can adopt L2–L6 without also committing to L15, and so the
wire formats can evolve independently.  All three sections
(`typedwasm.ownership`, `typedwasm.regions`, `typedwasm.capabilities`)
are independently optional from the verifier's perspective; absence is
"no claim made," not "claim of compliance."

=== Wire format — `typedwasm.regions`

Little-endian, byte-aligned, lenient on truncation (matches
`section.rs::LenientReader`).

----
u16le   version              (= 1)
u32le   region_count
for each region (in index order, 0..region_count-1):
    u32le  name_len
    u8[]   name              (UTF-8, no NUL terminator)
    u32le  field_count
    for each field (in declaration order):
        u32le  field_name_len
        u8[]   field_name    (UTF-8)
        u8     kind          (0 = Scalar,
                              1 = PtrOwning,
                              2 = PtrBorrow,
                              3 = PtrExclusive)
        u8     wasm_ty       (0 = U8,  1 = U16,  2 = U32,  3 = U64,
                              4 = I8,  5 = I16,  6 = I32,  7 = I64,
                              8 = F32, 9 = F64, 10 = WBool,
                              0xFF = N/A — set for pointer kinds)
        u32le  target_region (0xFFFFFFFF if kind = Scalar;
                              else index into this section's region table)
        u8     nullability   (0 = NonNull, 1 = Nullable)
        u32le  cardinality   (1 = single value, n>1 = fixed-length array
                              of n elements, 0 = unbounded /
                              dynamic-bounds — verifier treats as L5
                              "needs runtime check")
    u32le  region_byte_size  (∑ over fields of cardinality × sizeOf(wasm_ty);
                              redundant w.r.t. field table; verifier
                              cross-checks)
----

==== WBool wire width — pinned at 4 bytes (resolves #94)

`WBool` (wire codepoint `10`) occupies **4 bytes on the wire**, accessed
via wasm's standard `i32.store` / `i32.load` opcodes (with the
convention `0 = false`, nonzero = `true`). Producers SHALL NOT emit
`i32.store8` / `i32.load8` for `WBool` fields in v1 — the narrower
encoding is reserved for a future `WBoolPacked` variant in a v2 of this
section (separate `wasm_ty` codepoint, not a width-flag on `WBool`).

Rationale:

. **Producer reality.** Both current producers
  (https://github.com/hyperpolymath/affinescript[AffineScript] —
  `lib/codegen.ml:180-190+:373`,
  https://github.com/hyperpolymath/ephapax[Ephapax] —
  `src/ephapax-wasm/src/lib.rs:2937-2944`) lower source-language
  `Bool` → `ValType::I32` and emit `i32.store` / `i32.load`. Pinning
  at 4 bytes matches every shipping producer without codegen changes.
. **Spec self-consistency.** `Region.idr` is amended in this PR to
  `sizeOf WBool = 4` (was `1`) so that `schemaSize` and `computeOffsets`
  agree with the wire reality. `alignOf = sizeOf` (Region.idr:113)
  carries the change through to field-alignment math.
. **Verifier simplicity.** A single canonical width means no new
  `MixedWidthBoolean` error variant; `region_byte_size` cross-check is
  deterministic per schema.
. **Future flexibility.** A 1-byte `WBoolPacked` (or named-equivalent)
  remains the v2 escape hatch for size-conscious producers — additive,
  not a wire-width flag on the existing `WBool` codepoint.

The lenient mixed-width resolution sketched in
https://github.com/hyperpolymath/typed-wasm/issues/94[#94]'s
"Recommendation §A" is rejected because it makes `region_byte_size`
producer-choice-dependent (the same schema would have different
`schemaSize` values depending on which producer emitted it) and forces
a new verifier error variant for marginal flexibility.

Mapping to the spec types:

[cols="1,3"]
|===
| Wire field          | Idris2 spec
| `region_count`, `region` table | `List Region` (lookup-by-index)
| `field_count`, `field` table   | `Schema` (per region)
| `name`, `field_name`           | `String` (via `fieldName`)
| `wasm_ty`                      | `WasmType` (11-variant enum)
| `kind`                         | `PtrKind` (extended with `Scalar`)
| `nullability`                  | `Nullability`
| `cardinality`                  | feeds `InBounds idx count` for L5
| `target_region`                | foreign-key into `Region` table (L2)
|===

=== Wire format — `typedwasm.capabilities`

----
u16le   version              (= 1)
u32le   capability_count
for each capability (in index order):
    u32le  name_len
    u8[]   name              (UTF-8)
u32le   function_count
for each function:
    u32le  func_idx          (index into wasm function section)
    u32le  required_count
    u32le[required_count]    required_capability_indices
                             (indices into capability table above;
                              must be strictly increasing → trivially
                              encodes `DistinctCaps`)
----

Mapping to `ResourceCapabilities.idr`:

* The flat capability table = `CapabilitySet`.
* Strictly-increasing required indices structurally encode
  `DistinctCaps` (no duplicates, fixed comparison order).
* Per-function `required_capability_indices` ⊆ capability-table is the
  raw data the verifier feeds to `ContainedIn`.
* L15-C (call-graph monotonicity / `CallCompatible`) is **deferred to
  v1.4.x** (per LEVEL-STATUS) and needs a separate per-call-site grant
  record; out of scope for v1.

=== v0 producer surface

As of v0 (proposal acceptance), no shipping producer exercises the full
wire surface defined above.  Concretely:

* `wasm_ty` codepoints `0`–`5` (`U8, U16, U32, U64, I8, I16`) — no
  producer language surfaces narrow integer types at the type-system
  level.  AffineScript emits `{I32, I64, F32, F64}` only (`lib/wasm.ml`);
  Ephapax exposes `BaseTy { Unit, Bool, I32, I64, F32, F64 }` only
  (`src/ephapax-syntax/`).  `WBool` (codepoint `10`) is emitted by
  both producers but lowered to `i32` on the wire.
* `kind` codepoints `1`–`3` (`PtrOwning, PtrBorrow, PtrExclusive`) are
  exercised only by AffineScript.  Ephapax codegen erases the borrow
  distinction (`SharedBorrow`/`ExclBorrow`) before wasm emission and
  collapses to `Linear`/`Unrestricted` only, so an ephapax-emitted
  `typedwasm.regions` section would carry `kind ∈ {0, 1}` exclusively.
* `cardinality` values other than `1` — variable-cardinality fields
  require array-as-field support, which no producer ships at v0.
  AffineScript arrays are length-prefixed runtime objects;  Ephapax
  uses runtime list handles.  Neither emits fixed-array struct fields.
* The `typedwasm.capabilities` section as a whole — L15 has **no
  producer at v0**.  The wire format is specified for forward
  compatibility, but no current producer emits this section.

These codepoints are **reserved** (forward-compatible): consumers
MUST accept them when they appear (the lenient-reader contract
applies) and MUST NOT reject a v0 module that omits them.  A producer
that begins emitting a reserved codepoint in v1.x triggers either:

. an **additive** version bump if only the wire shape extends, or
. a **breaking** version bump if the semantics of an existing codepoint
  change.

Implementations of `crates/typed-wasm-verify/` should NOT preallocate
handling for reserved codepoints at v0; hitting one in a v0 module
signals either a future-version producer (reject with
`UnsupportedCarrierVersion`) or a producer bug (reject with the
appropriate `OwnershipError` variant).

=== Versioning policy

Both new sections start with `u16le version = 1`.  Future versions:

* **Additive** changes (new trailing fields per record) MAY ship as
  the same major version, since the lenient reader will silently
  ignore the new bytes on a v1 consumer.  This is the same forward-
  compatibility contract as `typedwasm.ownership`.
* **Breaking** changes bump the version and the verifier rejects
  unknown versions with a fresh `OwnershipError`-style variant.
* `typedwasm.ownership` is unchanged by this proposal.  Adding a
  version prefix to it is desirable but is its own change (latent
  issue — track separately).

=== Producer obligations

A conforming producer that emits either new section MUST:

. Emit it with a value of `version` it knows the consumer accepts.
. Use **stable region indices** within a single module (used as
  foreign keys both in this section and, eventually, by L14/L16
  protocol carriers).
. Either emit *all* fields of *all* regions it accesses, or emit
  *none* — partial carriers are interpreted as "no claim made about
  unlisted fields" and L2 will flag any access to an unlisted field.
. For L15: emit only capabilities actually declared by the source
  module; do not synthesise.
. **Canonical emit order** (recommended, not enforced):
+
[loweralpha]
.. `typedwasm.ownership`
.. `typedwasm.regions`
.. `typedwasm.region-imports` (proposal 0003)
.. `typedwasm.capabilities`
.. `typedwasm.access-sites` (proposal 0002)
.. `typedwasm.capability-grants` (proposal 0004)
+
Rationale: matches the runtime dependency graph — `access-sites`
foreign-keys into `regions`, `capability-grants` foreign-keys into
`capabilities`, and `region-imports` companions `regions`.
**Consumers MUST NOT depend on this order**: the verifier reads
sections by custom-section name, so a non-conforming producer that
emits in any other order is still parseable. The canonical order
exists solely so that two producers' emission of the same logical
module produces byte-equal carrier-section sequences (useful for
cross-producer module comparison via `cmp` or `diff`, and for
deterministic content-addressing of typed-wasm modules).

=== Consumer obligations (verifier)

`crates/typed-wasm-verify/` will gain:

. `section.rs` — `parse_regions_section_payload`,
  `build_regions_section_payload`, `parse_capabilities_section_payload`,
  `build_capabilities_section_payload`.  Same lenient-reader pattern.
. `verify.rs` — new passes `verify_region_binding` (L2),
  `verify_type_compat` (L3), `verify_null_safety` (L4),
  `verify_bounds` (L5), `verify_result_type` (L6),
  `verify_capabilities` (L15).
. `lib.rs` — new `OwnershipError` variants per failure mode, plus a
  top-level `VerifyError::UnsupportedCarrierVersion`.

Each pass is gated behind a cargo feature
(`unstable-l2`, …, `unstable-l15`) until the proposal is accepted, so
the v1.0 verifier surface is unchanged.

== Alternatives considered

=== A. One omnibus section

Fuse regions + capabilities into a single `typedwasm.metadata`
section.

*Rejected.* L2–L6 and L15 are orthogonal concerns and have different
adoption curves: an early producer may want regions without yet
declaring capabilities, or vice versa.  A single section forces both
to land at the same version.  Wire-format evolution is also entangled
— a breaking change to the capability layout invalidates region data
that was fine on its own.

=== B. Reuse `typedwasm.ownership`

Extend the existing section's per-entry payload with optional fields.

*Rejected.* The ownership section is keyed by function index and
carries per-function signatures; regions and capabilities are
module-scoped (regions) or have a different per-function shape
(required-caps lists).  Cramming them in would either break the
current parser or require a sub-record discriminator on every entry.
The split-section approach keeps each codec linear and per-concern.

=== C. Reuse a wasm-component-model interface type

Encode region schemas as wasm component-model record types and let
the component-model machinery carry them.

*Rejected for v1.*  Component-model adoption in the typed-wasm
producer set is too early — AffineScript and Ephapax both currently
target core wasm.  Worth revisiting in Phase 4 (Tooling / DX) once
`wasm-tools component new` is in the producer cookbook.

=== D. Embed in `name` section

Use the standard `name` custom section's free-form sub-sections to
piggy-back schema data.

*Rejected.* The `name` section is for debug names; tools strip it
under `-Os`.  Schema/capability data is load-bearing for
verification, not debug info, and must not be optimised out.

== Open questions

. **String table.** The format above duplicates region names if a
  field's `target_region` is referenced from multiple fields.  Worth
  it to add a single shared string table at the front of the
  section?  Trade-off: smaller modules (~5–15% on representative
  AffineScript fixtures, untested) vs. an extra indirection in the
  parser.  Default: ship v1 inline, add string table in v2 only if
  measurements justify it.

. **Cardinality `0 = unbounded` sentinel.** Should the verifier treat
  unbounded as L5-unprovable (downgrade), or refuse to admit the
  section at all?  Source-side AffineScript today doesn't emit
  unbounded regions; the sentinel is reserved for future dynamic-
  bounds work.  Default: downgrade with a verifier diagnostic, do
  not refuse.

. **Endianness of UTF-8 strings.** Trivially answered (none — UTF-8 is
  a byte stream) but worth being explicit in the spec to avoid
  producer drift.

. **Per-function vs per-call-site capability annotations.** L15-A
  (required-caps per function) is enough for v1; L15-C (per-call-site
  grants) needs a separate annotation that ideally lives in a third
  section (`typedwasm.capability-grants`) so the v1.4 → v1.4.x
  transition is purely additive.  Defer the wire format for grants to
  a follow-up proposal.

. **Interaction with `noSpoofing` (L13 cross-module).** A multi-module
  setting needs the importing module's region table to refer to the
  exporting module's region by something other than a local index.
  Two options: (a) a separate `typedwasm.region-imports` section
  that mirrors wasm's standard `(import …)` syntax; or (b) extend the
  per-region record with a `(producer-name, region-name)` pair when
  cross-module.  Out of scope of v1 (single-module L2–L6 is the v1
  milestone); needs its own proposal.

. **Access-site carrier (RESOLVED — option A).** Discovered during
  the pre-stage codec in PR #77: this proposal's `typedwasm.regions`
  section says *which regions exist* but does **not** say which
  `(region_id, field_id)` any individual wasm load/store targets.
  The source-level checker sees `region.get $r .f`; post-codegen
  that's just `i32.load offset=N align=A`, with the `($r, .f)`
  annotation gone. So this proposal is sufficient for
  L2-the-spec (schema agreement) but insufficient for
  L2-the-enforcement (every typed access resolves to a declared
  region/field). Owner-resolved 2026-05-27 (see typed-wasm#78):
  **adopt option A — a per-instruction access-site carrier
  (`typedwasm.access-sites`) mapping
  `(func_idx, instruction_byte_offset) → (region_id, field_id)`**.
  Wire-format design for that section lands in a follow-up proposal
  (`docs/proposals/0002-...adoc`); the L2 verifier pass
  (`verify_region_binding`, omitted from PR #77) is gated on
  that proposal's acceptance.

== Acceptance criteria

. Reviewed and signed off by maintainers of `affinescript` and
  `ephapax` (the only current producers of `typedwasm.ownership`).
. Wire format reviewed against the Idris2 spec types in `Region.idr`,
  `Pointer.idr`, `ResourceCapabilities.idr` — every wire field maps
  cleanly to a spec witness. *(Satisfied — see Appendix A below.)*
. A draft codec lands in `crates/typed-wasm-verify/src/section.rs`
  behind cargo features (`unstable-l2`, `unstable-l15`); round-trip
  tests show parse(build(x)) = x for non-empty fixtures.
. A draft section in
  `spec/type-safety-levels-for-wasm.adoc` documents the new sections
  alongside the existing `typedwasm.ownership` description.
. Cross-repo issues are filed against `affinescript` and `ephapax`
  for codegen of the new sections (out of scope of *this* proposal —
  this proposal only defines the wire format).

After acceptance, this file is promoted to an ADR under
`docs/decisions/` (per `docs/proposals/README.adoc`'s status legend)
and the level-table in `LEVEL-STATUS.md` gains "verifier (carrier-
backed)" status columns for L2–L6 and L15.

== Appendix A — Wire-vs-Idris2-spec mapping (Criterion 2)

This appendix satisfies acceptance Criterion 2 ("wire format reviewed
against the Idris2 spec types — every wire field maps cleanly to a spec
witness"). Each wire field below is paired with the Idris2 type / value
that it encodes, and every cross-section invariant the wire carries is
named against the spec lemma it corresponds to. The reference codec is
`crates/typed-wasm-verify/src/section.rs` (landed in PR #107).

=== A.1 `typedwasm.regions` ↔ `Region.idr` + `Pointer.idr`

[cols="2,3,2", options="header"]
|===
| Wire field
| Idris2 spec witness
| Notes

| `u16le version = 1`
| (codec invariant — no spec mapping)
| Future major bumps land in a separate proposal; v1 verifier rejects
  unknown versions per `parse_regions_section_payload` (section.rs:418).

| `u32le region_count`
| `length : List Region -> Nat` applied to the per-module region list
| The wire-side list is dense (region IDs are 0..region_count-1);
  matches `Region.idr`'s record-of-list shape.

| Per-region `utf8 name`
| `Region.regionName : String` (Region.idr:253)
| UTF-8 byte sequence with explicit length prefix; no NUL terminator.
  String identity (not embedding) is what cross-module agreement
  reasons over.

| Per-region `u32le field_count`
| `length : Schema -> Nat` where `Schema = List Field` (Region.idr:158)
| Empty schema (`field_count = 0`) is admissible — corresponds to
  `LayoutNil` and a region with `schemaSize = 0`.

| Per-field `utf8 field_name`
| `Field.MkField` name component (Region.idr:127); extracted by
  `fieldName : Field -> String` (line 132)
| Field-name injectivity (Region.idr:360 `fieldNameInj`) holds on the
  Idris2 side; the wire format preserves the same identity because
  identical bytes ↔ identical `String`.

| Per-field `u8 kind` (0=Scalar, 1=PtrOwning, 2=PtrBorrow, 3=PtrExclusive)
| `Pointer.idr::PtrKind` (line 39): Owning/Borrowing/Exclusive plus the
  out-of-band "not a pointer" case
| `Scalar` is a wire-side discriminant carrying the "this field stores
  an inline value, not a pointer" case that `Pointer.idr` represents
  implicitly by not using `Ptr` at all. The bijection on the
  three pointer cases is exact.

| Per-field `u8 wasm_ty` (0..10 = U8..WBool, 0xFF = NotApplicable)
| `Region.idr::WasmType` (line 34): 11 variants
| `NotApplicable` (0xFF) is emitted when `kind != Scalar` (the field
  type semantics come from the target region). v1 has no `WBool`
  store-width pin (see open question #94 / typed-wasm#94).

| Per-field `u32le target_region`
| Spec-side: `Ptr kind (lookupField target_region).schema life null`
  parameterisation (Pointer.idr:74)
| Foreign key into the same section's region table. `NO_TARGET_REGION`
  (0xFFFFFFFF) sentinel when `kind == Scalar`. Verifier enforces
  `target_region < region_count` when `kind != Scalar` — this is the
  operational form of the spec-level `Schema` indexing on `Ptr`.

| Per-field `u8 nullability` (0=NonNull, 1=Nullable)
| `Pointer.idr::Nullability` (via Levels.idr) — used as the `null`
  parameter of `Ptr kind schema life null`
| The lenient decode (`Nullability::from_byte`) treats unknown bytes
  as `NonNull`, which is the safer interpretation per the spec's
  L4 (null safety) discipline.

| Per-field `u32le cardinality`
| `Region.count : Nat` (Region.idr:258)
| Sentinel `0 = unbounded/dynamic`; matches the spec only when
  cardinality > 0 (open question §"Cardinality `0 = unbounded`
  sentinel" defers full coverage to L5 verifier downgrade).

| Per-region `u32le region_byte_size`
| `schemaSize : Schema -> Nat` (Region.idr:204)
| Redundant w.r.t. the field list; verifier MAY recompute and compare
  (proposal §"Producer obligations" ¶4). When the producer's value
  diverges from the recomputed `schemaSize`, the verifier flags a
  carrier-self-inconsistency error.
|===

=== A.2 `typedwasm.capabilities` ↔ `ResourceCapabilities.idr`

[cols="2,3,2", options="header"]
|===
| Wire field
| Idris2 spec witness
| Notes

| `u16le version = 1`
| (codec invariant)
| Same versioning policy as regions.

| `u32le capability_count`
| `length : CapabilitySet -> Nat` applied to `ModuleCaps.declared`
  (ResourceCapabilities.idr:218)
| The wire capability table IS the module's declared capability set —
  one wire entry per `CapabilityName` in `declared`.

| Per-capability `utf8 name`
| `CapabilityName.capName : String` (ResourceCapabilities.idr:67)
| The newtype wrapping discipline (`MkCapabilityName`) preserves
  identity on the wire as raw UTF-8 — type system on the spec side
  refuses to confuse capability names with arbitrary strings; wire
  side simply names the bytes.

| `u32le function_count`
| Per-module count of `FunctionCaps owner` values
| Not directly a spec witness; bridges wire to the per-function
  records below.

| Per-function `u32le func_idx`
| (wasm function index — bridges spec to emitted wasm)
| No direct spec mapping; the Idris2 side reasons in terms of
  `FunctionCaps owner` records, not wasm function indices. The wire
  side names the index because that is what the verifier needs to
  attach the requirement to a concrete code-section function.

| Per-function `u32le required_count`
| `length : CapabilitySet -> Nat` applied to `FunctionCaps.required`
  (line 241)
| Producer MAY emit 0 — corresponds to `pureFunctionCaps`
  (ResourceCapabilities.idr:248) and `FunctionCaps.required = []`.

| Per-function `u32le[] required` (strictly increasing)
| `FunctionCaps.required : CapabilitySet` (line 241), with the
  strict-increasing invariant encoding `DistinctCaps` (line 104) AND
  serving as the verifier's foreign-key check
| The strict-increasing invariant is the *operational counterpart* of
  three spec-side facts at once:

   1. **`DistinctCaps required`** — no index appears twice. The
      strict-increasing form trivially implies uniqueness.

   2. **`ContainedIn required declared`** (L15-B soundness, line 312)
      — each index < `capability_count`. The verifier's
      `verify_capabilities_from_module` pass (PR #109) checks this
      directly, raising `CapabilityIdxOutOfRange` on violation.

   3. **Canonical-order producer obligation** — equal `required` sets
      have equal wire byte sequences (encoding determinism).

  Parser-side `sort_unstable` + `dedup` (section.rs:760) is a
  defence-in-depth normalisation: a producer that regresses on the
  strict-increasing obligation still yields a verifier result
  consistent with the spec, but the wire-level guarantee is degraded.
|===

=== A.3 What is NOT carried on the wire (deliberate)

The Idris2 spec types have several relations and proofs that v1 of the
carriers deliberately does NOT encode:

[cols="2,3", options="header"]
|===
| Spec construct
| Why not on the wire / where it lives

| `ContainedIn required declared`
  (L15-B explicit proof witness)
| The verifier RECONSTRUCTS the proof obligation by checking each
  `required[i] < capability_count`. The reconstructed check is sound
  because the verifier IS the trusted base for L15-B on emitted
  wasm; carrying the explicit witness would duplicate the same
  information.

| `CallCompatible caller callee`
  (L15-C call-graph monotonicity)
| Deferred to a separate `typedwasm.capability-grants` section
  (typed-wasm#96) in a v1.4.x follow-up proposal. v1 enforces L15-A
  (DistinctCaps) and L15-B (ContainedIn) only; L15-C falls back to
  the producer's source-level checker.

| `LayoutValid schema`
  (per-field offset fits within instance size; no field overlap)
| The verifier RECOMPUTES `computeOffsets`/`schemaSize` from the
  wire-carried field list and compares to the wire-carried
  `region_byte_size`. The proof obligation is operational, not
  carried.

| `SchemaEq s1 s2`
  (cross-module schema equivalence — Region.idr:306)
| v1 is single-module. Cross-module schema agreement is the explicit
  scope of a future `typedwasm.region-imports` follow-up (open
  question #5 / typedwasm#95) — the comparison logic uses the
  wire-carried region + field tables directly without an
  intermediate witness.

| `RegionDisjoint r1 r2`
  (byte-disjoint regions — Region.idr:439)
| Runtime / loader concern; the wire format intentionally does not
  pin region base addresses (those are wasm-side `(memory ...)` init
  data). Disjointness is enforced at allocation time by the host
  runtime, not by the carrier verifier.

| `ExclusiveWitness schema`
  (Pointer.idr:163 — no-aliasing for exclusive pointers)
| L7 (aliasing safety) is carried by the `typedwasm.ownership`
  section (Linear/SharedBorrow/ExclBorrow tags per parameter), NOT
  the regions carrier. The regions carrier only attests to schema
  structure, not to per-handle aliasing facts.
|===

=== A.4 Soundness shape

Combining the per-field mappings (A.1) with the operational
reconstructions (A.3) gives the following claim, which proposal 0001
asserts (and the verifier in PR #109 + the codec in PR #107 enforce):

[NOTE]
====
For any module emitting `typedwasm.regions` and `typedwasm.capabilities`,
**there exists a corresponding Idris2 spec-level
`(Region[], ModuleCaps, FunctionCaps[])` value** whose constructor
inhabitation requires exactly the proofs the verifier already checks at
the wire level — namely:

* `WasmType` decoder soundness (lenient by design — unknown ⇒ safer
  default per A.1 nullability + WasmTy notes).
* `FieldKind` ↔ `PtrKind` bijection on the three pointer cases.
* `target_region` foreign-key check (when `kind != Scalar`).
* `region_byte_size` self-consistency vs `schemaSize`.
* `DistinctCaps` via strict-increasing `required[]` (degraded but
  recoverable via parser-side `sort + dedup`).
* `ContainedIn required declared` via `required[i] < capability_count`
  (verifier pass — PR #109).

L15-C (`CallCompatible`), `SchemaEq` (cross-module), `RegionDisjoint`,
and `ExclusiveWitness` are explicitly out of scope of v1 and tracked
under the open-questions section above.
====

This satisfies Criterion 2 *as a write-up*. A future task — not
required for `[accepted]` — is to encode the same mapping as Idris2
property tests (`src/abi/` would gain a `WireSchemaEquiv.idr` showing
`encode/decode` round-trips preserve the spec witnesses listed in A.1
+ A.2). That work is filed as a follow-up after acceptance.

== Appendix B — Producer-readiness checklist (closes #97)

Surfaced in the paired producer reviews of proposals 0001 + 0002
(ephapax#165 §3 + §6 + affinescript#402 §4 + §7, both 2026-05-30):
the §"Producer obligations" section enumerates what a conforming
producer must *do at emission time*, but understates **what a producer
must already have in its IR** to be capable of emitting populated
sections at all.

This appendix tabulates the IR prerequisites for each carrier
section, the producer-side status at v1, and the roadmap-issue
identifier in each producer's tracker where the gap is named.

NOTE: A producer that emits a carrier section without satisfying its
IR prerequisites will emit an empty or synthetic section that the
verifier will treat as "no claim made about anything," falsifying
the intent of the carrier. **The all-or-nothing rule from §"Producer
obligations" ¶3 implies: do not emit a section you cannot populate.**

=== B.3 Use this checklist

When any producer's tracker (AffineScript Roadmap C1/C2/C3 issues,
Ephapax codegen issues, future third-party producer tickets) opens
a work item for emitting a new carrier, that issue SHOULD
cross-reference this appendix and the corresponding §B.1 row. This
makes the multi-quarter IR work explicit rather than discovering it
ad-hoc during downstream codegen sessions.

The verifier-side adoption (codecs + verify passes in
`crates/typed-wasm-verify/`) is INDEPENDENT of producer-side
readiness — the verifier can ship parsing + validation for a carrier
that no producer yet emits (the verifier just sees an absent section
and returns `Ok(())`). This appendix only tracks the producer side.
